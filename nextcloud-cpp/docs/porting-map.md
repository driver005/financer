# What is ported

Paths are relative to the Nextcloud tree in `docs/nextcloud-server`. **Ported** means the behaviour exists
here and is tested; **Reduced** means a deliberate subset (stated); **Replaced** means done differently;
**Not ported** means it does not exist here.

## Kernel

| Nextcloud | Status | Here |
| --- | --- | --- |
| `lib/private/Server.php`, `lib/public/IContainer.php`, `IServerContainer` | Replaced | `ServiceRegistry`: named services with string arguments instead of a typed DI container |
| `lib/private/EventDispatcher`, `lib/public/EventDispatcher` | Reduced | `EventBus`: synchronous, string topics with a `*` suffix pattern, string payloads, failing handlers isolated |
| `lib/private/Route`, `lib/public/Route`, every `appinfo/routes.php` | Reduced | `Router`: method + pattern, `{name}`, `{*rest}`, 404/405/OPTIONS/HEAD. No route requirements (regex), no URL generation |
| `lib/private/App/AppManager.php`, `appinfo/info.xml` | Replaced | `Kernel` + the plugin table in the ABI: name, version, description, requirements, ordering, skip on failure. Enabling is the `plugins` setting. No app store, no per-user app enablement, no `info.xml` |
| `lib/private/Config.php`, `config/config.sample.php`, `AppConfig` | Reduced | `Config`: one text file with `[plugin]` sections, read-only at run time; what changes while the server runs lives in the `settings` plugin (see below) |
| `lib/private/Log`, `lib/public/ILogger.php` | Reduced | `Logger`: levels, stderr sink, per-plugin source |
| `occ`, `core/Command` | Reduced | `CommandRegistry` + `nextcloud occ`: `list`, `status`, `plugin:list`, `config:get`, `background:run|list`, plus what plugins add. No interactive prompts: secrets come from `OC_PASS` |
| `lib/private/BackgroundJob`, `cron.php` | Reduced | `JobScheduler`: interval jobs added by plugins (`host.add_job`), run once a second while serving and by `occ background:run`. No job queue with arguments, no persistence of the last run |
| `lib/private/Authentication` (login chain) | Reduced | the request pipeline: app password (`auth.token`), then password (`auth.authenticate`), then second factor (`auth.second_factor`, `X-NC-OTP`). Basic auth and Bearer tokens (`auth.bearer*`, used by `oauth2`); `/public.php/` is left to the plugin that serves it (share token as user name). No sessions, cookies or CSRF tokens. **SAML 2.0** (`saml` plugin, counterpart of `user_saml`, one identity provider): SP-initiated Web SSO, `GET /index.php/apps/user_saml/saml/login` (HTTP-Redirect with a deflated AuthnRequest), `POST .../saml/acs` (HTTP-POST), `GET .../saml/metadata`. The response is checked with `libxml2` (no DTD, exclusive canonicalization of the signed element and of SignedInfo) and BoringSSL: the assertion must be covered by an enveloped signature (RSA-SHA256/384/512, or ECDSA-SHA256/384/512 with a P-256, P-384 or P-521 certificate; the algorithm has to be the one of the configured certificate's key, the message does not choose it) that verifies with the one configured certificate (`idp_certificate_file`, never a key from the message), with a single reference to the signed element whose ID occurs once, plus issuer, audience, recipient, `InResponseTo`, validity window, one use per request and per assertion. The tests sign with `xmlsec1` (an independent implementation) and try signature-wrapping variants, a weaker signature, wrong audience/recipient/issuer/time and DTD documents. A person is created as an account and gets an app password (shown once). **Single logout**, identity-provider-initiated, HTTP-POST binding: with `[saml] idp_slo_url` set, `POST .../saml/logout` takes a `LogoutRequest` that must carry an enveloped signature of the configured certificate (same rules as for assertions), come from the configured provider, be addressed to this endpoint, be recent (10 minutes) and not expired, name exactly one unencrypted `NameID`, and be new (a request counts once); the app passwords that sign-in made for that person (service `tokens.revoke_named`) are revoked and the answer, a `LogoutResponse`, goes back to `idp_slo_url` (HTTP-Redirect, unsigned) with the `RelayState`. The metadata advertises the endpoint. Tested with requests signed by `xmlsec1`. **Service provider initiated logout and signed requests**: with `[saml] sp_private_key_file` (RSA) the `AuthnRequest` and the `LogoutRequest` that go out by redirect carry `SigAlg` and `Signature` (the HTTP-Redirect binding signs the query string as sent; checked with `openssl` in the tests), and with `sp_certificate_file` the metadata lists the certificate and says `AuthnRequestsSigned`. `GET .../saml/sp-logout` (signed in with the app password) revokes the sign-in app passwords of that person and sends the browser to `idp_slo_url` with a `LogoutRequest` naming their NameID; the identity provider's answer lands on `GET .../saml/logout` as a page. **Logout by the redirect binding**: the identity provider may also send its `LogoutRequest` by `GET` (deflated in the query); the signature is then the one over `SAMLRequest=...&RelayState=...&SigAlg=...` as sent (RSA or ECDSA, checked with the configured certificate, an unsigned or repeated parameter is refused, and so is an inflated message of more than 256 KiB), and the request is used once like the posted one. **Encrypted assertions**: with `sp_private_key_file` set, an `EncryptedAssertion` is decrypted with that RSA key (session key by RSA-OAEP, with SHA-1/256/384/512 and MGF1 as the XML names them, `rsa-1_5` is refused; data by AES-128/192/256-CBC or AES-128/256-GCM) and then needs a valid signature like any assertion: its own, or the response's around the cipher text. The metadata then also lists the certificate for `use="encryption"`. Tested with encryptors that are not this code: `openssl` (OAEP key wrapping with several digests, `rsa-1_5` for the refusal, AES-CBC) as the baseline, and `xmlsec1` as a cross-check where its version can make the same (versions differ in what they accept). White space between elements is kept when reading (a response printed with indentation is signed with it). Not done: ECDSA signatures, ECDH key agreement for encryption, AES-192-GCM, logout requests of the identity provider by redirect binding (they must be posted), checking the identity provider's `LogoutResponse`, signed LogoutResponses by POST, IdP-initiated login, several providers, role/group mapping |
| `lib/private/DB`, `lib/public/IDBConnection.php`, `lib/private/Migration` | Reduced | the `db` plugin: SQLite, `db.exec|query|migrate`, migrations applied once per plugin and version in a transaction. No Doctrine/query builder, no other database engine |
| `status.php` | Ported | `GET /status.php` (adds the plugin list) |
| `ocs/`, `lib/private/OCS` | Reduced | `nc::http::ocs()` builds the OCS v2 JSON envelope; no XML format, no `format=` negotiation |
| `remote.php`, `public.php`, `index.php` | Replaced | one router; the URLs `/remote.php/dav/...` and `/s/<token>` are kept so clients work |
| HTTP server (Apache/nginx + PHP-FPM) | Replaced | `HttpServer`: HTTP/1.1, one thread per connection, `Content-Length` and chunked bodies, `Expect: 100-continue`, **TLS 1.2+ with BoringSSL** (`tls_cert`, `tls_key`), no keep-alive, no HTTP/2, no certificate reload without a restart |
| `lib/private/AppFramework` (controllers, middleware, DI of controllers) | Reduced | `sdk/plugin/include/nextcloud/app.h`: `nc::app::App` registers routes with `RouteOptions` (access PUBLIC/USER/ADMIN, plain or OCS error format) instead of annotations; `Middleware` with `before_controller`, `after_controller`, `after_exception`; ready-made session, admin and error middleware (`use_defaults()`); handlers throw `HttpError`. Used by every plugin that has signed-in or administrator-only routes (`settings`, `theming`, `updatenotification`, `webhook_listeners`, `workflowengine`, `user_status`, `weather_status`, `notifications`, `activity`, `comments`, `systemtags`, `tokens`, `twofactor`, `trashbin`, `versions`, `lookup`, `users`, `groups`, `mail`, `oauth2`, `previews`, `federation`, `calendar`, `cloud`). Routes that stay on `add_route` are the ones that decide for themselves: anonymous protocol routes (OCM, public links, the token endpoint's client authentication), WebDAV and CalDAV/CardDAV handlers (they answer 401/403/207 in DAV terms) and discovery redirects. No dependency injection, no request-body binding to typed parameters, no CSRF token (the API is Basic/Bearer authenticated, not cookie based).  |
| `lib/private/Security`, CSP, rate limiting, brute force protection | Reduced | CSP and `nosniff` on downloads, constant time comparisons, uniform answers for bad tokens and unknown users, request smuggling shapes refused. **Brute-force protection** (`bruteforce`, Nextcloud's `Throttler`): the HTTP server sets `X-NC-Remote-Addr` from the connection (a header from the wire is dropped; `X-Forwarded-For` counts only from `trusted_proxies`, read from the right) and the kernel asks `auth.throttle` before it looks at credentials: from `max_attempts` failures (default 10) of one address within `window_seconds` (1800) the answer is 429 with `Retry-After` (0.25 s after the last failure, doubling with each failure, at most the window; nobody is held in a sleeping thread, and refused requests are not counted). A good password clears the failures of that address for that account only. `whitelist` takes exact addresses and CIDR ranges. In memory: a restart forgets the counts. No general rate limiting of other endpoints |
| `lib/private/Template`, themes, JS front end (`core/`, `apps/*/src`) | Not ported | the runner serves APIs only |

Downloads of 1 MiB and more are streamed: the owner's server's answer is passed on piece by piece through the plugin interface (a response can carry a body stream), so a big file never sits in memory whole; other answers (listings, small files, chunked answers) are held in memory (`[federation] max_remote_file_mb`, default 64). Outgoing requests check the certificate and the host name, never follow redirects and refuse local addresses unless `allow_local` is set. Requests between servers are signed (Ed25519 over request target, host, date and body digest; the key is in the discovery document and cached ten minutes), unsigned ones are refused with `require_signatures = true`, and `trusted_servers` limits whom this server talks to or listens to. **Group shares**: share type 9 (`group@server`) offers the share to every member of that group on the other server; one member declining leaves it to the others. The people of other servers go into the system address book (see CardDAV). Not ported: pulling address books from other servers, re-shares across servers; **Signatures**: by default Ed25519 (this project's variant of the HTTP-signatures draft); with `[federation] signature_algorithm = rsa-sha256` a server signs the way Nextcloud does (RSA-2048, PKCS#1 v1.5 over SHA-256, `Signature` header with `headers="content-length date digest host"`, key published as `publicKey: {keyId, publicKeyPem}`), and requests signed either way are accepted; an RSA-signed request made with the system's `openssl` is part of the tests. Not checked against a real Nextcloud server, and not the RFC 9421 or JWKS variants Nextcloud also offers |
